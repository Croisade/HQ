# Notes — jellyfin

## 2026-08-11

**Recurring bug found and mitigated**: newly-imported episodes for a *brand-new* series (one Jellyfin has never indexed before) can show up as findable via a generic item search, but not through `/Shows/{id}/Episodes` — the actual endpoint the web/app clients use to render a season page. Symptom from the user's side: "Unable to find a valid media source to play," and/or only a subset of episodes visible (sometimes just one). Hit twice in one day, both times on a new anime series where [sonarr](../sonarr/README.md) imported many episodes (5, then 10) in a tight few-minute burst — the per-import `updateLibrary` notification call Sonarr fires (see [sonarr's notification setup](../sonarr/README.md)) is a small targeted update, and doesn't reliably finish building the full Series→Season→Episode relationship tree under that kind of burst load for a series with no prior tree to extend.

Fix for an already-affected series: force a full metadata refresh, not just a rescan —
```
POST /Items/{seriesId}/Refresh?Recursive=true&MetadataRefreshMode=FullRefresh&ImageRefreshMode=FullRefresh&ReplaceAllMetadata=false&ReplaceAllImages=false
```
A plain library scan (`/Library/Refresh`) is not sufficient — it finds files but doesn't reliably rebuild the relationship tree either.

**Durable mitigation applied**: Jellyfin's built-in `Scan Media Library` scheduled task defaulted to a 12-hour interval — far too infrequent to self-heal this in any reasonable time. Shortened to hourly (`IntervalTicks: 36000000000`, via `POST /ScheduledTasks/{id}/Triggers`) as a safety net, since Jellyfin's own scans are incremental/cheap when nothing's actually changed. This doesn't eliminate the underlying gap, but bounds how long a newly-added series can stay broken to about an hour without needing manual intervention.

If this recurs on a series you *can't* wait an hour for, trigger the full-refresh command above directly rather than waiting on the schedule.

## JellyBridge (discover content from Jellyseerr)

Installed to browse/request unowned content directly from Jellyfin (any client, including native apps, since it's a real library rather than a web-injected UI element — see [jellyseerr's README](../jellyseerr/README.md) for why this was preferred over Jellyfin-Enhanced). Repository: `https://raw.githubusercontent.com/kinggeorges12/JellyBridge/refs/heads/main/manifest.json` — confirmed the actively-maintained fork (202 stars, pushed within the last two weeks) over two inactive personal forks of it with the same name.

**Storage**: separate dedicated volume (`data/jellybridge` → `/jellybridge`), not under the real `/media` mount (which stays read-only by design).

**Structure as of 2026-08-12**: replaced the original two merged libraries (`Discover Movies`/`Discover Shows`, one giant unfiltered pool each) with **12 per-brand libraries** — one Movies + one Shows library per streaming service in `NetworkMap` (Netflix, Disney+, Hulu, HBO Max, Amazon Prime Video, Paramount+). Enabled via `UseNetworkFolders: true` in the plugin's persisted config, which reorganizes the filesystem into `/jellybridge/Movies/<Network>/` and `/jellybridge/Shows/<Network>/` subfolders instead of one flat folder per media type. Each subfolder is registered as its own Jellyfin `VirtualFolder` (`POST /Library/VirtualFolders?name=<Network> Movies&collectionType=movies` with `LibraryOptions.PathInfos` pointed at that specific subfolder) — this is what actually makes it a real, separately-browsable library rather than just a filesystem detail (Jellyfin's normal library grid doesn't expose folder structure; only its separate, rarely-used "Folders" view does).

`AddDuplicateContent` (default `true`) means the same title can legitimately appear in multiple brand libraries if it streams on more than one service — expected, not a bug.

Sizes vary a lot by service: most came in at the full `MaxDiscoverPages` cap (~160 items each), but Paramount+ (`id: 531`) only returned 4 movies / 5 shows — a real TMDB catalog-data limitation for that provider ID/region, not a sync failure.

Old flat (non-networked) placeholder folders from before this restructure were deleted (`rm -rf` on every top-level item that wasn't one of the 6 network subfolder names) since nothing referenced them anymore.

**Real gotchas hit, in order**:
1. ~~`SelectedNetworks` never persists via the plugin's `Configuration` save endpoint, has to be passed directly in every sync call body instead~~ — **corrected 2026-08-12, this was wrong.** Checked the plugin's actual source (`ImportDiscoverContentController.cs`): `POST /JellyBridge/SyncDiscover` takes **zero request parameters** — it just calls `_syncService.SyncFromJellyseerr()` with no args, which reads entirely from the plugin's *persisted* configuration. Every body param we'd been passing on each sync call (`SelectedNetworks`, `MaxDiscoverPages`, `DefaultMoviesPromo`, `DefaultSeriesPromo`, `UseMixedMediaLibrary`) was silently ignored the whole time — confirmed by checking `GET /Plugins/{pluginId}/Configuration` and finding `MaxDiscoverPages: 2` (the original default) despite the sync script always sending a different value. The Configuration endpoint **does** persist correctly (`POST /Plugins/{pluginId}/Configuration` with the full config object) — we just never actually called it. Real config lives in `NetworkMap` (not `SelectedNetworks` — that field doesn't exist in the persisted schema at all), which had been empty this whole time, meaning discover content was never actually filtered to specific streaming networks despite that being the original intent. **Fixed 2026-08-12**: populated `NetworkMap` with 6 real networks (see Structure section above). JSON field names for each entry are lowercase/camelCase (`id`, `name`, `country`, `displayPriority`) matching the `[JsonPropertyName]` attributes on `JellyseerrNetwork`, **not** the PascalCase C# property names — sending `{"Id": 8, "Name": "Netflix", ...}` silently produces a garbage all-zero entry instead of an error, since the plugin's JSON deserializer isn't case-insensitive. Verify by reading the config back after every write; a correctly-set entry echoes back with both its alias fields (`id`/`name`) and the underlying base-class fields (`provider_id`/`provider_name`) populated identically.
2. Movies need an actual placeholder video file to register as a proper "Movie" item (Series don't — they're metadata-only containers). `DefaultMoviesPromo`/`DefaultSeriesPromo: true` are correctly persisted plugin config fields (confirmed via `GET /Plugins/{pluginId}/Configuration` — both already `true`), same story as above: they work via saved config, not via the (nonexistent) sync-call body.
3. Every sync marks all synced items with a `.ignore` file (hidden from Jellyfin), every single time — including content that was already visible from a previous sync. This is NOT limited to genuine duplicates of already-owned content, despite what the plugin's docs imply ("Hide Existing Discover Content"). Confirmed non-owned content (Spider-Man movies, Supernatural, etc.) getting hidden on every sync regardless. Fix: delete the `.ignore` files after every sync, before the next library refresh.
4. **The plugin's own built-in scheduled task doesn't work.** Confirmed directly: triggering `JellyBridge Sync` via Jellyfin's task scheduler completes in ~0ms with nothing processed. Given item 1 above, the params-not-in-body theory for *why* was wrong, but the observed behavior (task does nothing) still stands and is unexplained — **do not rely on the plugin's own schedule.**
5. **`MaxDiscoverPages` fixed 2026-08-12**: was stuck at the default `2` (→ ~40 items/library) since it was always being set via the ignored sync-call body. Fixed properly via `POST /Plugins/{pluginId}/Configuration` (plugin id `8ecc808cd6e9432f9219b638fbfb37e6`), set to `8` → up to ~160 items/library (applies **per network** in `NetworkMap`, see Structure section — 6 networks × up to 160 movies + 160 shows each). To change again, GET the current config, edit the field, POST the whole object back (partial updates not tested).
6. **Sync script's `.ignore`-clearing command silently broke when `UseNetworkFolders` was enabled.** It used `find /jellybridge/Movies /jellybridge/Shows -maxdepth 2 -name ".ignore" -delete`, tuned for the old flat layout (`Movies/<item>/.ignore` = depth 2 from the `Movies` root). Once items moved to `Movies/<Network>/<item>/.ignore` (depth 3), that maxdepth silently stopped finding anything — 296 `.ignore` files sat there hiding most of the newly-synced content across the per-brand libraries until caught by comparing library item counts against raw folder counts on disk. Fixed by dropping the depth limit entirely in the script.

**What's actually running now**: `systems/jellyfin/scripts/jellybridge-sync.sh` (credentials in a gitignored `.env` alongside it, `.env.example` documents the keys needed) calls `SyncDiscover` (no body — see gotcha 1), clears `.ignore` files (no depth limit — see gotcha 6), then triggers a library refresh, via a host cron job at 6am daily (`crontab -l` on `homelab-server`). Log at `data/jellybridge-sync.log`.

Also worth knowing: re-syncing without increasing `MaxDiscoverPages` mostly returns the *same* items each time, since TMDB's discover/trending rankings don't rotate much day to day — currently set to `8`. Change it (or `NetworkMap`) via the plugin's persisted `Configuration`, not the sync script.

**Large syncs take real time to index.** Adding the 6-network `NetworkMap` in one go produced ~1600 new placeholder items across 12 libraries; Jellyfin's scanner processes libraries one at a time (not in parallel) and took roughly 10+ minutes to settle. Poll `GET /Library/VirtualFolders` and watch each library's `RefreshStatus` (`Queued`/`Active`/`Idle`) rather than assuming a triggered refresh has finished quickly. Deleting a large batch of orphaned folders afterward also re-triggers a full rescan via the real-time file watcher (`EnableRealtimeMonitor`) — expect another wait, not an error.

**"Only 2 recommendations" — home-screen Latest widget, not the library itself.** Reported as "Discover Shows only has 2 recommendations." The actual library was fine (confirmed 39-40 `Series` items via `/Users/{id}/Items?ParentId=...`, both as admin and as the affected user). The culprit was the **home screen's "Latest in Discover Shows" row** (`/Users/{id}/Items/Latest`): for a `tvshows`-typed library, that widget surfaces recent *episodes*, not series. Every series here has exactly one synthetic placeholder episode (`Season 00/S00E9999.mp4`, all byte-identical, all from the same sync batch), and Jellyfin's Latest query only ever picked 2 of them — likely some internal dedup/grouping quirk triggered by every "episode" being the same file. `Discover Movies` doesn't have this problem since its Latest widget surfaces `Movie` items directly and each has a distinct title.

Fix: excluded `Discover Shows` from both users' home-screen Latest widget (`POST /Users/{id}/Configuration` with the library's Id appended to `LatestItemsExcludes`) rather than trying to fix the underlying episode dedup — that row was never meaningful for a synthetic discover library anyway (users are meant to browse the library grid and favorite to request, not "watch" a placeholder labeled `S00E9999`). `Discover Movies` was left alone since its Latest row displays correctly.

When `Discover Shows` was replaced by the 6 per-brand Shows libraries (see Structure above), the same exclusion was applied proactively to all 6 new Shows library IDs for both users before the bug could resurface — any *new* `tvshows`-typed JellyBridge library needs this same treatment.
